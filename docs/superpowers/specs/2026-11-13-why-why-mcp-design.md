# why-why-mcp 設計

日付: 2026-11-13
状態: 確認待ち

## 目的

障害やバグの原因を、エージェントが**なぜなぜ分析**で掘るための MCP サーバーです。

- 各段で、いろいろな方向の「なぜ」を候補として出します。1本の線で終わらせません。
- 候補は、有力なものから順に掘ります(最良優先)。掘らなかった候補も「未調査の枝」として残し、後で戻れるようにします。
- 有力かどうかの評価には、Cloudflare の決定モデル **Clef** を使えます。事実で決まることはツールで確かめ、Clef の確信が低い所だけエージェント(Claude など)が判断します。
- 分析の木をブラウザで見たい。返信はエージェントのターミナルに戻したい。この2つは **Plannotator Inbox** にそのまま任せます(ユーザー決定)。

## 目標・目標外・失敗とみなすもの

**目標**
- エージェントが、MCP の道具だけで木を作り、育て、評価し、描ける。
- 描いた木を Plannotator Inbox に送ると、人がブラウザで木を見て、ノードにコメントできる。返信はそのままエージェントのセッションに届く。
- Clef が使えない環境でも、エージェントの判断で同じ流れが回る。
- Claude Code と Codex のどちらからでも同じ道具で使える。

**目標外**
- 独自の返信の仕組み、独自の Web サーバー、独自の画面(Plannotator Inbox を使う)。
- 「なぜ」の候補を MCP 自身が文章生成すること(候補はエージェントが出す)。
- 見つけた原因のコード修正。

**失敗とみなすもの(動いていても失敗)**
- 木の形が崩れる(親のないノード、循環、同じ枝の二重登録)。
- 評価が低いという理由で、枝が消える。却下した枝も、理由つきで必ず残す。
- 事実で裏付けていない枝が、裏付けた枝と見分けられない。
- 秘密情報(API トークンなど)がリポジトリや描画結果に入る。公開リポジトリのため。

## 作り方の案(ユーザーが A を選択)

| 案 | 内容 | 評価 |
|---|---|---|
| **A. MCP + Inbox で表示**(採用) | MCP が木を持ち、描いた木をエージェントが Inbox に送る | 木の形を MCP が守れる。どのエージェントからも同じ道具で使える。更新のたびに新しいメッセージになる |
| B. スキル + 小さなスクリプト | 手順をスキルに書き、保存と描画だけスクリプトで行う | 最も手軽だが、木の扱いがエージェントの手作業に近くなり崩れやすい |
| C. MCP + 専用の木の画面 | 常に最新の木を専用ページで見せ、返信は Inbox | 最新を見やすいが、作るものが最も多く、見る場所が2つに分かれる |

## 前提と制約

- 公開リポジトリ(nowly-lab/why-why-mcp、MIT)。秘密情報は環境変数からだけ読む。
- Plannotator Inbox の仕様(調査結果):
  - メッセージ本文の ` ```mermaid ` は図として、` ```html ` は小さなページとして描かれる(最大高さ 480px、外部へのアクセスは https のみ)。
  - 添付した HTML ファイルはビューアで開け、人のコメントは返信と一緒にエージェントへ戻る。
  - 返信がセッションに戻るのは、Claude Code(Plannotator プラグイン)、Codex 0.149 以降など。それ以外は `read_thread` で後から読む。
- MCP サーバーの説明文(instructions)は Claude Code の上限 2,048 文字に収める。
- Clef(公式ドキュメントで確認済み):
  - `POST https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/run/@cf/cloudflare/clef`(または `clef-flash`)
  - 入力: `state`(文字列か構造化データ)、`questions`(1〜64個。`noul` / `choice` / `score`)
  - 出力: `noul` は「はい」の確率、`choice` は選択肢ごとの確率、`score` は確率で重み付けした段階の値(0 が最低)
  - 料金: 入力 100 万トークンあたり 0.24 ドル、出力は無料。文脈は 65,536 トークンまで。

## 設計

### 技術

- TypeScript、Node.js 22 以上。MCP は `@modelcontextprotocol/sdk`(stdio)。
- 配布: `npx github:nowly-lab/why-why-mcp`(npm 公開は後で判断)。
- テスト: `node:test`。Clef は `fetch` を差し替えて試す。

### 保存

- 分析ごとに1つの JSON ファイル: `<プロジェクト>/.why-why/<分析ID>.json`。
  - プロジェクトは、MCP を起動したフォルダ(環境変数 `WHY_WHY_DIR` で変更可能)。
  - 書き込みは一時ファイルに書いてから置き換え、途中で壊れないようにする。
- 描画結果も同じフォルダ: `<分析ID>.html`、`<分析ID>.mmd`(どちらも Inbox に添付する)。
- Git に入れるかはプロジェクトの判断に任せる(README で説明する)。

### データの形

```
Analysis
  id, title
  problem: 事実で書いた問題(いつ・どこで・何が・どうなったか)
  status: open | closed
  nodes: Node[]
  createdAt, updatedAt

Node
  id, parentId(根は問題そのもの = null)
  text: 「なぜ」の答え
  viewpoint: 仕組み・道具 | 人・体制 | 手順・プロセス | 検知 | 前提・外部
  state: candidate(未調査の枝) | digging(掘っている) | leaf(葉。対策を立てる所)
       | rejected(却下。理由つき) | hypothesis(事実で確かめられず止めた)
  evidence: { kind: log | code | git | metric | doc | other, ref, summary, supports: true|false }[]
  evaluation: {
    source: clef | agent
    supported: 0〜1(事実で裏付けられている確率)
    sufficient: 0〜1(この原因だけで親の現象が起きる確率)
    likelihood: 0〜1(有力度)
    impact: 0〜1(影響の大きさ)
    preventable: 0〜1(仕組みを変えれば防げる確率 = 葉かどうか)
    lowConfidence: true|false
    at
  }
  reason: 却下・仮説で止めた理由
  countermeasure: 葉の対策
```

### 道具(MCP ツール)

| 道具 | 何をするか |
|---|---|
| `start_analysis` | 問題を事実で書いて、分析を始める |
| `add_whys` | あるノードの下に「なぜ」の候補をまとめて足す(観点つき)。同じ親に同じ文がすでにあれば足さない |
| `add_evidence` | ノードに事実(ログ・コード・git など)を記録する |
| `evaluate` | 候補を評価する。Clef が使えれば Clef に聞き、使えなければ「エージェントが判断すべき問い」を返す |
| `record_judgment` | エージェントの判断を評価として記録する(Clef の確信が低かった所、Clef がない環境) |
| `next_branch` | 未調査の枝から、次に掘るものを1つ選んで返す(最良優先)。掘る価値のある枝がなければ「終わり」と返す |
| `update_node` | 状態を変える(掘る・葉にする・却下・仮説で止める)。葉には対策、却下と仮説には理由が必須 |
| `render` | 木を HTML と Mermaid に描き、ファイルの場所と、Inbox の本文にそのまま入れられる Mermaid の文を返す |
| `get_analysis` / `list_analyses` | 分析を読む・一覧する |

### 評価(Clef)

- 1回の呼び出しで、評価するノードごとに次の問いをまとめて聞く(64問の上限内で分割する)。
  - `supported`(`noul`): 記録した事実から、この原因は裏付けられているか
  - `sufficient`(`noul`): この原因だけで、親の現象が起きるか
  - `likelihood`(`score`: 低い・中くらい・高い・ほぼ確実)
  - `impact`(`score`: 小さい・中くらい・大きい・重大)
  - `preventable`(`noul`): 仕組みを変えれば、この原因を防げるか
- `state` には、問題・親までの道筋・そのノード・記録した事実を入れる。
- `score` の値は 0〜1 に直して保存する。
- 確率が 0.35〜0.65 の問いがあれば `lowConfidence` にし、エージェントに判断を求める。
- 設定: `CLOUDFLARE_ACCOUNT_ID`、`CLOUDFLARE_API_TOKEN`(Workers AI の権限)、`WHY_WHY_CLEF_MODEL`(既定は `clef-flash`)。未設定なら Clef は使わない。
- Clef の失敗(通信・上限超え)は、その評価だけ「エージェントの判断が必要」として返し、木には何も書かない。

### 次の枝の選び方

- 対象: 状態が `candidate` の枝。
- 優先度 = `likelihood × impact`。事実の裏付け(`supported`)が高いものを同点のとき上にする。
- 未評価の枝は「先に評価が必要」と返す。
- 終わり: 残った候補がすべて優先度のしきい値(既定 0.2)未満のとき、または候補がないとき。
- 枝は消さない。しきい値未満の枝も一覧には残る。

### 描画

- HTML: 1ファイルで完結(外部スクリプトなし)。木を左から右に描き、状態ごとに色と記号を分ける。各ノードに観点・評価・事実・対策を表示する。Inbox の添付ビューアで開き、ノードにコメントできる。
- Mermaid: `flowchart LR`。ノード数が多いとき(既定 40 超)は、却下した枝を省いた要約版にして、省いたことを書く。
- 描画結果にトークンなどの秘密情報は含めない(事実の要約は記録したまま描く)。

### Inbox との使い方(エージェント向けの手順)

MCP の説明文と、リポジトリ内のスキル(`skills/why-why/SKILL.md`)に書く。

1. `start_analysis` で始める
2. 各段で観点ごとに候補を出し `add_whys`
3. 事実を確かめて `add_evidence`
4. `evaluate`(必要なら `record_judgment`)
5. `next_branch` で選んだ枝を掘る。葉まで来たら対策を書いて `update_node`
6. 区切りごとに `render` し、Mermaid を本文に、`.mmd` と HTML を添付にして Inbox に送る
7. 人の返信やコメントを受けて木を直し、5 に戻る。`next_branch` が「終わり」と返したら、対策の一覧を送る

## 細かい決まり(設計者の判断)

ビルダー確認で出た点を、次のように決めました。

1. **ノードへのコメントの付け方**: Inbox では、添付した Mermaid ファイル(`.mmd`)はノードをクリックしてコメントでき、コメントにはノードの ID が付いて戻る。HTML はピンか文字の選択でコメントする。そこで `render` は両方を作り、エージェントは**`.mmd` と HTML の両方を添付**する。Mermaid のノード ID は木のノード ID と同じにし、HTML でも各ノードに ID(例 `N3`)を見える形で書く。
2. **評価は問いごとに持つ**: `evaluation` の各値は `{ value, source: clef | agent, at }` とし、`lowConfidence` は問いごとに付ける。`record_judgment` は指定した問いだけを上書きする。古い評価は `history` に残す。
3. **事実を足したら評価は古くなる**: `add_evidence` は、そのノードの評価に `stale: true` を付ける。`next_branch` は古い評価の枝を「先に評価が必要」として返す。
4. **「事実で裏付けあり」の定義**: `supports: true` の事実が1つ以上あること。`supported` の確率は優先度の計算にだけ使う。描画では、裏付けありの枝と裏付けなしの枝を印で分ける。
5. **秘密情報**: 保存するときに、よくあるトークンの形(`Bearer ...`、`sk-...`、`ghp_...`、長い16進や Base64 の文字列、`password=` など)を `[伏せ字]` に置き換える。保存・Clef への送信・描画のどれも、置き換えた後のデータしか使わない。MCP の説明文でも、秘密を記録しないよう伝える。
6. **状態の移り方**:
   - `next_branch` は提案するだけで、状態は変えない。エージェントが `update_node` で `digging` にする。
   - `rejected` と `hypothesis` は、理由を付ければ `candidate` に戻せる(人のコメントで見直すとき)。
   - `leaf` には対策が必須。`preventable` は参考で、`leaf` にする条件にはしない。
   - 分析を閉じるには、`digging` の枝が残っていないこと。閉じた後も読むことと描くことはできる。

## 出し方と使い始め方(ユーザー決定、2026-11-13)

- 最初の公開は main へのマージまで。npm には公開しない(`npx github:nowly-lab/why-why-mcp` で使う)。
- README・道具の説明・スキルは英語を基本にし、日本語の説明も付ける。観点名などの木の中の言葉は日本語。
- マージ後、手元の Claude Code(`claude mcp add --scope user`)と Codex(`codex mcp add`)に登録する。
- 確認のとき、本物の Clef を1〜2回呼んで、返事の形を確かめてよい。
- implementation リポジトリに `why-why-mcp-tips` スキルを足す(設計者の判断)。

## ビルダーに任せること

- ファイル構成、関数の分け方、HTML の見た目の細部。
- ID の作り方(短く、ぶつからないもの)。
- しきい値の初期値の微調整(ただし設定で変えられるようにする)。
